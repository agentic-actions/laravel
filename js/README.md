# @agentic-actions/client

Typed calls and copilot rows for [Agentic Actions for Laravel](https://github.com/agentic-actions/laravel#readme). `php artisan actions:typescript` writes `resources/js/agentic/actions.ts`, one typed definition per action route, and this package runs them. It also reads the copilot's chat stream: a live row for each tool the agent runs, and one refresh of the page when those tools write.

It has five entries:

- **`@agentic-actions/client`** has no dependencies. It holds `action()`, `uri()`, `newKey()` and `callAction()` over `fetch`, which sends the XSRF cookie to the page's own origin only. `onTouched()` hears the keys a success made stale. Then come the error classes, `messageSegments()`, `actionRows()` and `applyActionPart()` for a message's words and `data-action` parts, `approvalCard()` for the confirmation a message still waits on, and `elicitation()` for the form it still waits on, with the types of MCP's form-mode elicitation. `viewsOf()`, `formatCell()` and `refreshView()` read, write and refresh the tables a message shows, with the `data-view` part's types. Last, `createActionSync()` turns done rows into one refresh at a time, holds it while an editor registered in `editors` has unsaved work, and runs it by itself once none has.
- **`@agentic-actions/client/inertia`** runs on `@inertiajs/core`. `installInertiaReload()` reloads touched props through Inertia's router, and `inertiaApply()` is the refresh `createActionSync()` runs on Inertia.
- **`@agentic-actions/client/react`** runs on Inertia React. `useAction()` is Inertia's `useHttp` for an action. `useActionSync()` refreshes the page after the copilot writes, and `useActionEdits()` registers an editor it must wait for. `<ActionActivity>` shows the rows as an unstyled, accessible list, `<ApprovalCard>` shows one waiting confirmation with its two buttons, and `<ElicitationForm>` renders any MCP form-mode elicitation as an accessible form. Importing this entry installs the Inertia reload, and it stays under 4.5 KB gzipped.
- **`@agentic-actions/client/views`** runs on React alone. `<ActionTable>` draws a table a message shows as a plain, unstyled table, and the entry re-exports the root's `viewsOf()`, `formatCell()` and `refreshView()`, so a React page imports all of it from one place. It stays under 1.5 KB gzipped.
- **`@agentic-actions/client/ai-sdk`** runs on `ai` 7 alone. `actionsChat()` and `actionsTransport()` serve `useChat` or `new Chat()`. They post only the newest message, and send the XSRF header to the page's own origin only. Of a confirmation, they post the person's answer and never the tool's input, and they send a step's answers by themselves once each waiting call has one. `answerElicitation()` answers a waiting form. `turnOutcome()` tells how a turn ended, and `refusalMessage()` reads the server's sentence from an error.

Writes made elsewhere reach an open page through the change feed. Give `createActionSync()` or `useActionSync()` the group's feed route, `feed: { url }`, where the URL is `POST {group prefix}/actions/_changes` (the route `actions._changes` in a group without a name prefix). The page then polls it every 15 seconds (`interval` changes that, in milliseconds, and never below one second) while it is visible. It pauses after 10 minutes with no pointer or keyboard input. The next input, or the page turning visible again, polls at once, though never within a second of the last poll or while one is in flight. The keys other writes touched join the same refresh as a done row's: coalesced, held while an editor is dirty, and applied by `apply()`. Those writes include MCP calls, queued jobs, another person on the same tenant, and another tab. The feed answers only a signed-in session. A 401, 403, 404 or 419 stops polling for good. A 429, a server error or a network error waits for the next interval. `useActionSync()` reads `feed` at mount, like its other options, so a page whose feed URL changes remounts the component that calls it, for example with `key={feedUrl}`.

When the copilot calls a Destructive or External action, the turn pauses on a card the server built: the action's own sentence and rows, which the client shows as text. `approvalCard(messages.at(-1))` returns it while its call waits, and `<ApprovalCard approval={approval} onAnswer={(approved) => addToolApprovalResponse({ id: approval.id, approved })} />` answers it. The next waiting card, if any, shows once the first has an answer. The route and the agent are in the "Confirmations" section of [docs/copilot.md](https://github.com/agentic-actions/laravel/blob/main/docs/copilot.md).

When the copilot calls an action that asks for what the model left out, the turn pauses on a form the server built, in the shape of MCP's form-mode elicitation. `elicitation(messages.at(-1))` returns it while its call waits, and `<ElicitationForm key={form.id} params={form.params} labels={form.labels} onAnswer={(result) => answerElicitation(chat, options, form.id, result)} />` answers it. The form uses native controls and the browser's own checks, opens on the server's defaults, shows which app asks, and always offers Decline and Cancel. `answerElicitation()` first checks an accept with a Precognition request, so the action's own errors show under their fields and nothing is sent; then the person's answer goes out on the answered tool part, once, with the step's other answers. The model reads which fields were filled, never their values. A host that draws its own controls reads `form.params`, which is the standard's, and answers through `answerElicitation()` the same way; `classNames` styles the built-in form. The action's side is in [docs/asking.md](https://github.com/agentic-actions/laravel/blob/main/docs/asking.md).

When the copilot calls an action that shows a table, a `data-view` part follows its row: the table the person sees, built on the server from the action's declared columns, with `at`, when its rows were read, and `ref` when the action is on the web. `viewsOf(message)` returns a message's tables in order, and `<ActionTable key={view.id} view={view} refreshUrl="/actions/_views" />` draws one: the caption, a header per column, numbers aligned to the end of their cells (which follows a right-to-left page), a note with the number of rows shown when they were cut, and the time. Refresh shows only when the view has a `ref` and the page gives `refreshUrl`, the group's `_views` route without the ref (`{group prefix}/actions/_views`). It is disabled while it runs. It runs the action again as the person, shows the fresh rows and their time, and hands them to `onRefresh`, so a chart drawn beside the table can follow; a failed refresh keeps the table. `formatCell()` writes each cell with `Intl` in the `locale` prop, else the page's `lang`, else English, which a malformed locale also gets. A percent is a fraction (0.25 shows 25%), a date shows the day it names in any time zone, a datetime the person's own time, true shows ✓, and false and null show nothing. On a server-rendered page, pass `locale`; datetimes format in the viewer's time zone, so a page that renders them on the server should render the table on the client only. Labels and cells are always text, never HTML, and `classNames` styles each part. For a chart, `table.chart` names the type and the x and y keys, and the app draws `table.rows` with its own chart library, which must treat labels and cells as untrusted text. A page without React reads, writes and refreshes its tables with the root's `viewsOf()`, `formatCell()` and `refreshView()`. The action's side is in [docs/data.md](https://github.com/agentic-actions/laravel/blob/main/docs/data.md).

Each definition is also a plain `{ url, method }` pair, so Inertia's `<Form action>`, `useForm` and `useHttp` take it as is. Generated definitions use POST. `callAction()` sends the input as the body, so a definition written with `action()` names POST, PUT, PATCH or DELETE, never GET: TypeScript refuses one, and `callAction()` throws before sending it. `ai`, Inertia and React are optional peers, so an app installs only what the entries it imports need. The copilot's server and panel are in [docs/copilot.md](https://github.com/agentic-actions/laravel/blob/main/docs/copilot.md).

The client ships inside the Composer package, so the app installs it from `vendor/` and its version always matches the PHP package's: `"@agentic-actions/client": "file:vendor/agentic-actions/laravel/js"`. It is also on npm (`npm install @agentic-actions/client`), where you install the same version as the Composer package. When the Composer package itself comes from a local path (a symlinked checkout with its own `node_modules`), add `resolve.dedupe: ['react', 'react-dom', '@inertiajs/core', '@inertiajs/react', 'ai', '@ai-sdk/react']` to your Vite config, so the client uses your app's React, Inertia and `ai` rather than the checkout's. `dedupe` reaches Vite only: for `tsc`, map `ai` to your app's copy with `"paths": { "ai": ["./node_modules/ai"] }` in `tsconfig.json`.
